# HTTP 특징

## HTTP 메시지로 거의 모든 것을 전송할 수 있다

HTML, TEXT, IMAGE, 음성, 영상, 파일, JSON, XML(API) 등 거의 모든 형태의 데이터를 HTTP 메시지에 담아 전송할 수 있다.
요즘은 서버 간 데이터를 주고받을 때도 HTTP를 사용한다.

## 기반 프로토콜

- **TCP** 기반: HTTP/1.1, HTTP/2
- **UDP** 기반: HTTP/3

## HTTP의 특징

- 클라이언트 서버 구조
- 무상태 프로토콜(스테이트리스), 비연결성
- HTTP 메시지
- 단순함, 확장 가능

## 클라이언트 서버 구조

- 요청(Request), 응답(Response) 구조로 이루어진다.
- 클라이언트는 서버에 요청을 보내고 응답을 대기한다. (응답이 없으면 무한 대기할 수도 있다)
- 서버는 요청에 대한 결과를 만들어서 응답한다.

## 무상태 프로토콜 (Stateless)

서버가 클라이언트의 상태를 보존하지 않는다.

- **장점**: 서버 확장성이 높다 (스케일 아웃에 유리)
- **단점**: 클라이언트가 필요한 데이터를 매번 추가로 전송해야 한다

### Stateful vs Stateless

서버가 이전 요청의 상태를 기억하는지 여부의 차이다.

**Stateful (상태 유지)**

```
클라이언트: 로그인
서버: 로그인 상태 기억
클라이언트: 장바구니 들어가기
서버: 아까 로그인한 유저에게 장바구니 보여주기
```

서버가 클라이언트의 상태를 저장해두고, 다음 요청에서도 그 상태를 활용한다.

**Stateless (무상태)**

```
클라이언트: A 상품 주문
서버: A 상품 주문 완료
클라이언트: A 상품 주문 취소 요청
서버: 누구세요? (이전 상태를 모름)
```

서버가 클라이언트의 상태를 보존하지 않기 때문에, 클라이언트가 필요한 정보를 매번 같이 보내야 한다.

```
클라이언트: 클라이언트1이 A 상품 주문
서버: 클라이언트1이 A 상품 주문 완료
```

이렇게 하면 서버는 이전 요청을 기억하지 않아도 현재 요청만으로 처리할 수 있다.

## HTTP가 Stateless를 지향하는 이유

- Stateless는 클라이언트의 요청을 **어떤 서버가 처리해도 문제가 없다**.
  상태를 서버에 보관하지 않기 때문에, 중간에 서버 장애가 발생해도 다른 서버가 이어서 응답해줄 수 있다.
- 이런 장점 때문에 **스케일 아웃(서버의 수평 확장)** 에 유리하다.

반대로 **Stateful**은 요청을 처리하려면 항상 같은 서버가 유지되어야 한다.
그래서 서버에 장애가 발생하면, 상태 정보가 없는 다른 서버는 이어서 작업을 처리할 수 없다.

## Stateless의 실무 한계

설계할 때 무상태로 설계할 수 있는 경우도 있고, 없는 경우도 있다.

- **무상태로 설계 가능한 예**: 로그인이 필요 없는 단순한 서비스 소개 화면
- **상태 유지가 필요한 예**: 로그인
  - 로그인한 사용자의 경우, "로그인했다"는 상태를 서버에 유지해야 한다.
  - 일반적으로 브라우저 쿠키 + 서버 세션 등을 이용해 상태를 유지하며,
    상태 유지는 **꼭 필요한 곳에서만 최소한으로** 사용한다.

## 비연결성 (Connectionless)

클라이언트와 서버 간 요청과 응답이 끝나면, 연결을 계속 유지하지 않는다는 개념이다.

- 예를 들어 클라이언트 1, 2, 3이 서버와 작업을 마쳤는데도 연결이 계속 유지된다면
  서버 자원을 계속 소모하게 된다.
- 그래서 HTTP는 하나의 요청과 응답이 끝나면 연결을 유지하지 않는 것이 기본 모델이다.

### 비연결성의 장점

- 일반적으로 빠른 속도로 응답한다.
- 1시간 동안 수천 명이 서비스를 사용해도, 실제로 서버가 동시에 처리해야 하는 요청 수는
  수십 개 이하로 매우 작을 수 있다.
- 서버 자원을 효율적으로 사용할 수 있다.

### 비연결성의 한계와 극복

- 매 요청마다 TCP/IP 연결을 새로 맺어야 한다 → 3-way handshake 시간이 추가로 든다.
- 웹 브라우저로 사이트를 요청하면 HTML뿐 아니라 자바스크립트, CSS, 이미지 등
  많은 자원이 함께 다운로드되는데, 매번 연결을 새로 맺으면 비효율적이다.
- 지금은 **HTTP 지속 연결(Persistent Connection)** 로 이 문제를 해결한다.

## 참고: 스테이트리스는 항상 기억해야 할 개념

같은 시간에 딱 맞춰 몰리는 대용량 트래픽(예: 수강신청, 명절 KTX 예매 등)을
서버 개발자들이 스테이트리스 특성을 잘 이해하고 구현해야
문제없이 처리할 수 있다. 서버 개발에서 어려운 업무 중 하나다.
