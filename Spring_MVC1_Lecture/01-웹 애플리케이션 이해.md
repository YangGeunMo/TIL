# 스프링 MVC - 웹애플리케이션 이해

## 웹 서버

- 클라이언트(웹 브라우저)의 요청을 받아 정적 콘텐츠를 HTTP 프로토콜로 응답하는 서버
- 정적 리소스를 제공한다.
  - 정적파일 HTML, CSS, JS, 이미지, 영상 등

## 웹 애플리케이션 서버(WAS - Web Application Server)

- 프로그램 코드를 실행해서 동적 콘텐츠를 생성하고 애플리케이션 로직을 처리하는 서버
  - 동적 HTML, HTTP API(JSON)
  - 서블릿, JSP, 스프링 MVC
- 클라이언트 요청 → WAS가 프로그램 실행 및 데이터 처리 → 동적으로 생성된 내용 응답 → 클라이언트에게 화면 표시

## 웹 시스템 구성

- WAS와 DB로만 시스템이 이루어져 있다.
- WAS는 정적 리소스, 애플리케이션 로직 모든 제공이 가능하다.
- WAS가 너무 많은 역할을 담당하면 서버 부하가 올 수 있다. 만약 WAS 장애 시 오류 화면도 표시할 수 없다.
- 애플리케이션 로직이 정적 리소스 때문에 수행이 어려울 수도 있다.
- 그래서 정적 리소스는 웹 서버가 처리하고 WAS는 중요한 애플리케이션 로직만 처리한다.

서블릿은 비즈니스 로직을 제외한 모든 HTTP 관련, TCP/IP 등을 관리해 준다.

### 서블릿 특징
<img width="811" height="417" alt="image" src="https://github.com/user-attachments/assets/58b4cfc5-0af8-4b69-9457-b3496e375ff4" />

- 서블릿은 HTTP 요청, 응답 정보를 제공해주는 HttpServletRequest, HttpServletResponse를 제공한다.
- 개발자는 HTTP 스펙을 편리하게 사용한다.

### 서블릿 요청, 응답 흐름
<img width="825" height="442" alt="image" src="https://github.com/user-attachments/assets/8defcf9b-1c5b-437c-aa53-cc7b587e1737" />

HTTP 요청 시:
- WAS는 Request, Response 객체를 만들고 서블릿 객체를 호출한다.
- 개발자는 Request와 Response 객체를 통해 요청 정보와 응답 정보를 편리하게 사용할 수 있다.
- WAS는 Response 객체에 담긴 내용을 HTTP 응답 정보로 생성하고 클라이언트에게 전송한다.

### 서블릿 컨테이너

- 서블릿 객체 생성, 초기화, 호출, 종료하는 생명주기를 관리한다.
- 서블릿 객체는 싱글톤으로 관리한다.
  - 요청이 들어올 때마다 계속 생성하는 건 비효율적이므로 서블릿 객체를 미리 만들어두고 재사용한다.
  - 싱글톤이므로 모든 고객 요청은 동일한 서블릿 객체 인스턴스에 접근한다.
  - 서블릿 컨테이너 종료 시 함께 종료된다.
  - 공용 변수 사용에 주의해야 한다.

### 동시 요청 - 멀티 쓰레드

- 서블릿 객체를 호출하는 건 쓰레드이다.
- 쓰레드 하나만 사용할 경우 단일 요청은 정상적인 기능을 수행하는데 다중 요청이 들어올 경우 처리 지연이 발생하면 요청한 클라이언트는 대기해야 한다.
- 그래서 요청마다 쓰레드를 생성해서 처리 지연이 발생해도 신규 쓰레드를 생성해서 작업을 처리하면 된다.

#### 멀티 쓰레드의 장점

- 동시 요청을 처리할 수 있다.
- 리소스(CPU, 메모리)가 허용할 때까지 처리 가능하다.
- 하나의 쓰레드가 지연되어도 다른 쓰레드는 정상 동작한다.

#### 멀티 쓰레드의 단점

- 쓰레드는 매우 비싸다.
  - 고객 요청이 들어올 때마다 쓰레드를 생성하면 응답 속도가 느려진다.
- 쓰레드는 컨텍스트 스위칭 비용이 발생한다.
- 쓰레드는 생성에 제한이 없다.
  - 고객 요청이 너무 많으면 CPU, 메모리 임계점을 넘어 서버가 죽을 수 있다.

#### 쓰레드 풀

- 쓰레드를 지정한 최대치까지 생성하고 관리한다.
- 만약 최대치를 넘을 경우 기다리는 요청을 거절하거나 특정 숫자만큼 대기하도록 설정할 수 있다.
- 사용한 쓰레드는 반납한다.

**쓰레드 풀의 장점:**
- 미리 생성되어 있어 자원(CPU, 메모리)을 절약하고 응답 시간이 빠르다.
- 최대치를 정했으므로 많은 요청이 들어와도 대응이 가능하다. (안전하게 처리)

**실무 팁:**
- WAS 주요 튜닝 포인트는 최대 쓰레드의 수 설정
  - 너무 낮으면 동시 요청이 많을 때 서버 리소스는 여유로운데 클라이언트는 응답 지연이 발생한다.
  - 반대로 너무 높게 설정하면 동시 요청이 많을 때 CPU, 메모리 임계점 초과로 서버가 다운된다.
  - 장애 발생 시
    - 클라우드면 서버 늘리기, 이후 튜닝
    - 클라우드가 아닐 경우 튜닝
- 적정 숫자는 애플리케이션 로직 복잡도, CPU, 메모리, IO 리소스 등 상황에 따라 다르다.
- 최대한 실제 서비스에 맞추어 성능 테스트 시도가 필요하다.
- 대부분의 멀티 쓰레드 처리는 WAS에서 담당한다. 개발자가 멀티 쓰레드 관련해서 신경 쓸 필요가 없다.

## HTML, HTTP API, CSR, SSR

### 정적 리소스

- 고정된 HTML 파일, CSS, JS 이미지, 영상 등 제공
- 주로 웹 브라우저
- 웹 브라우저에서 요청을 하면 Web Server에서 이미 생성된 리소스 파일을 응답해서 반환한다.

### HTML 페이지

- 동적으로 필요한 HTML 페이지를 생성해서 전달한다.
- 브라우저가 요청을 하면 WAS를 통해 DB에서 조회하고 그 데이터를 이용해 동적으로 HTML 생성
- 타임리프, JSP 등의 기술 사용

### HTTP API

- HTML이 아니라 데이터를 전달
- 주로 JSON 형식 사용
- 앱, 웹, 서버와 통신
- 데이터만 주고받고 UI가 필요하면 클라이언트가 별도 처리한다.

### 서버사이드 렌더링, 클라이언트 사이드 렌더링

#### SSR (Server Side Rendering)

- HTML 최종 결과를 만들어 웹 브라우저에게 전달한다.
- 정적인 화면을 사용
- 관련 기술: 타임리프, JSP

#### CSR (Client Side Rendering)

- HTML 결과를 자바스크립트를 사용해 웹 브라우저에서 동적으로 생성해서 적용
- 주로 동적인 화면에 사용, 웹 환경을 마치 앱처럼 필요한 부분부분 변경할 수 있음
- 예) 구글 지도, Gmail, 구글 캘린더
- 관련 기술: React, Vue.js → 웹 프론트엔드 개발자
